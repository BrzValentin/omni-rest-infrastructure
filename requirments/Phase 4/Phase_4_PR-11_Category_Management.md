# PR-11. Category Management

## Phase 4 — Menu Management

## Цель

Позволить владельцу ресторана полностью управлять категориями меню.

## Task 1. Database Schema for Menu Categories

### Цель
Создать структуру хранения категорий меню.

### Требования
- Создать таблицу `menu_categories`.
- Категория принадлежит одному ресторану.
- Поля:
  - `id`
  - `restaurant_id`
  - `name`
  - `display_order`
  - `created_at`
  - `updated_at`
- Название категории обязательно.
- `display_order` обязателен.
- Один ресторан может иметь множество категорий.
- При удалении ресторана категории удаляются автоматически (Cascade Delete).

### Критерии приемки
- Таблица успешно создается миграцией.
- Связь Restaurant → Categories работает.
- `display_order` сохраняется.
- Все ограничения БД работают корректно.

## Task 2. Category Model

### Цель
Создать модель категории.

### Требования
- Реализовать модель Category.
- Настроить связи: Category → Restaurant.
- Валидация:
  - `name` обязательно.
  - `restaurant_id` обязательно.
- Поддерживать timestamps.

### Критерии приемки
- Модель создается без ошибок.
- Связи работают.
- Валидация выполняется.

## Task 3. Create Category API

### Цель
Позволить владельцу создавать категории.

### Требования
Endpoint: `POST /menu/categories`

- Создание категории.
- Указание названия.
- Автоматическое определение `display_order` (новая категория добавляется последней).
- Категория создается только внутри ресторана владельца.

Проверки:
- Пустое название запрещено.
- Слишком длинное название запрещено.
- Нельзя создать категорию в чужом ресторане.

### Критерии приемки
- Категория успешно создается.
- `display_order` выставляется автоматически.
- Возвращается созданная категория.
- Некорректные данные возвращают ошибки валидации.

## Task 4. Rename Category API

### Цель
Позволить переименовывать категории.

### Требования
Endpoint: `PATCH /menu/categories/{id}`

- Изменение названия.
- Обновление `updated_at`.

Проверки:
- Категория существует.
- Принадлежит ресторану владельца.
- Название валидно.

### Критерии приемки
- Название успешно обновляется.
- Другие поля не изменяются.
- Ошибки возвращаются корректно.

## Task 5. Delete Category API

### Цель
Удаление категории.

### Требования
Endpoint: `DELETE /menu/categories/{id}`

Удаление возможно только владельцем ресторана.

Если категория содержит блюда — удаление запрещено.

Ошибка:
`Category contains dishes.`

Проверки:
- Категория существует.
- Принадлежит владельцу.
- Категория пустая.

### Критерии приемки
- Пустая категория удаляется.
- Категория с блюдами не удаляется.
- Возвращается понятная ошибка.

## Task 6. Category Ordering API

### Цель
Позволить менять порядок категорий.

### Требования
Endpoint: `PATCH /menu/categories/reorder`

Принимается массив ID.

- Проверяется принадлежность категорий ресторану.
- Обновляется `display_order`.
- Используется transaction.

### Критерии приемки
- Новый порядок сохраняется.
- Все категории получают новые `display_order`.
- Частичное обновление невозможно.
- Ошибки корректно обрабатываются.
